SESSION 3 — UPLOAD BEHAVIOUR: REPLACE VS AGGREGATE
────────────────────────────────────────────────────────────────────────────────

Q: How hard will it be to build the system such that it will aggregate all data
   it receives and also give the option to get analytics regarding a single
   file upload?

A: The core problem is that FIFO is stateful across time. A sell can only be
   calculated correctly if we have all prior buys. There is no meaningful
   "single-file FIFO result" in isolation.

   ┌──────────────────────────────────────────────┬───────────────────────────┐
   │ Feature                                      │ Complexity                │
   ├──────────────────────────────────────────────┼───────────────────────────┤
   │ uploads table + upload_id on transactions    │ Low                       │
   │ Positions computed on ALL data               │ Same as replace           │
   │ GET /uploads — list past uploads             │ Low                       │
   │ Per-upload analytics (FIFO isolated per file)│ Very hard / misleading    │
   └──────────────────────────────────────────────┴───────────────────────────┘

Q: Wait, I don't get it — can you simplify? The user uploads a file and sees
   data about the file. After that, the user uploads another file. Do we now
   show data as if the user uploaded one big file?

A: Upload 1: 50 transactions from January.
   Upload 2: 30 transactions from February.

   Replace mode: after Upload 2, the system forgets January. User sees only
   the 30 February transactions.

   Aggregate mode: after Upload 2, the system has 80 transactions combined.

   My honest recommendation for this assignment: go with replace. The assignment
   describes a one-shot workflow — "upload a file, see the results." Aggregate
   adds upload history UI, a reset feature, and filtering logic — none of which
   is in the assignment rubric. One upload = one dataset.

   DECISION: Replace-on-upload. → ADR 009.

SESSION 4 — SPEC REVIEW (27 QUESTIONS)
────────────────────────────────────────────────────────────────────────────────

Q1: When dealing with user input I think first about malicious code. How do we
    deal with that problem for Excel files?

A:  openpyxl with data_only=True never executes macros or formulas — it reads
    cell values only. We also validate MIME type AND extension, enforce a file
    size limit before parsing, and wrap everything in try/except for corrupt
    files. Added a security section to the spec.

Q2: How will we deal with very large row counts?

A:  openpyxl read_only=True streaming mode reads one row at a time — the whole
    file is never loaded into memory. Bulk inserts use SQLAlchemy's executemany
    (5,000 rows per flush). At 200k rows: ~4s to parse, ~20s to insert.

Q3: Is the assignment specific about what to do with a defective row?

A:  No. Our call: reject the entire file if any row fails validation. Stream the
    whole file once, collect all errors, return 422 with the full list. Nothing
    is saved. "If you've got 10,000 rows with 50 bad rows, the right answer is
    fix your data." → ADR 011.

Q7: Volatility analytics was defined by the assignment as an account that holds
    a lot of different stocks — please check that the spec is aligned with that.

A:  Your read is not what the assignment says. The exact words are "largest
    variation in total portfolio value" — a client whose total portfolio dollar
    value swings the most over time. Our spec already implements this correctly
    (simulate value at each transaction timestamp, measure max − min).

Q10: I will want to use ORM instead of full SQL queries.

A:   Switching to SQLAlchemy ORM. ADR 010 supersedes ADR 004. db/schema.py
     becomes db/models.py with mapped classes. Repositories use Session instead
     of Connection.

Q13: Maybe for this project we will just use an environment file to make things
     simpler for easy setup at every PC?

A:   Agreed. pydantic-settings reads .env natively. We commit .env.example with
     placeholder values. → ADR 012.

Q14: Does this architecture follow some design patterns?

A:   Yes, deliberately:
     - Layered Architecture — api → domain → db, dependencies only point downward
     - Repository Pattern — db/repositories/ abstracts all data access
     - Dependency Injection — FastAPI Depends() injects DB sessions into routes
     - Service Layer — domain/ is pure business logic, no HTTP or DB imports
     - Strategy/Protocol — SecretsProvider protocol for swappable secret backends

Q17: Do you consider this architecture modular enough to be easily testable?

A:   Yes, by construction. domain/ and ingestion/ are pure Python functions —
     unit tests need no DB, no HTTP client. db/repositories/ needs a DB but no
     HTTP. api/routes/ uses FastAPI's TestClient. Each layer is independently
     testable because dependencies are injected, not imported directly.

Q18: I thought of using Claude Design to have some sort of design system.

A:   Use Ant Design (antd) — built for data-heavy financial UIs, excellent table
     components, professional look out of the box. Use claude.ai artifact mode
     to generate a wireframe before writing a single React component.

SESSION 5 — FILE SIZE, ASYNC, AND RACE CONDITIONS
────────────────────────────────────────────────────────────────────────────────

Q: You said 50MB file size but only 200,000 rows — it seems conflicting.
   Also, don't you think the backend should be async?

A: File size inconsistency — you're right. A 50MB xlsx can hold ~2M rows, but
   I said limit to 200k. The fix: align them. At ~50 bytes/row compressed,
   200k rows ≈ 10MB. → File limit: 10MB + 200k rows.

   Async backend — yes, async def everywhere, but the two types of work differ:

   ┌─────────────────────────────┬───────┬──────────────────────────────────┐
   │ Operation                   │ Bound │ Why                              │
   ├─────────────────────────────┼───────┼──────────────────────────────────┤
   │ GET /clients (DB query)     │ I/O   │ Waits for PostgreSQL             │
   │ GET /analytics (DB queries) │ I/O   │ Waits for PostgreSQL             │
   │ openpyxl parsing            │ CPU   │ Pure Python XML parsing          │
   │ FIFO engine                 │ CPU   │ Sorting + iteration + arithmetic │
   │ Bulk DB inserts             │ I/O   │ Waits for PostgreSQL to write    │
   └─────────────────────────────┴───────┴──────────────────────────────────┘

   async def does nothing for CPU-bound work. For those sections we use
   asyncio.to_thread() to push them into a thread pool without blocking the
   event loop.

Q: Do we need to handle race conditions? I think the home assignment will be
   used by one user — but don't we want some scale resilience?

A:  Even for a demo, showing awareness of concurrency is the professional move.
    The specific risk: two simultaneous uploads truncate and rebuild the tables,
    resulting in corrupted mixed data.

    Solution: PostgreSQL advisory lock. One line at the start of the pipeline:
    SELECT pg_try_advisory_lock(12345)
    If false → return 409. Zero extra infrastructure.

SESSION 6 — ASYNC MODEL & SCALING
────────────────────────────────────────────────────────────────────────────────

Q: We decided on leaving the POST method that takes an Excel file synchronous.
   Can you explain why? Also, how many files can one uvicorn worker handle?

A: Two separate things here — terminology matters.

   The upload route IS async def internally (asyncio.to_thread for CPU-bound
   sections, AsyncSession for DB). But it is a BLOCKING HTTP CALL — the client
   waits for the full result before getting a response.

   The alternative (202 Accepted + job ID + polling) requires Celery + Redis.
   For a single-user demo, one blocking HTTP call is the right scope. → ADR 013.

   Concurrent capacity with one uvicorn worker:
   - UPLOADS: effectively 1 at a time (advisory lock). A second upload attempt
     from the same user gets 409 immediately — not queued.
   - GET REQUESTS: unlimited concurrently. Pure async I/O, never touches the lock.
   - The event loop is NOT frozen during an upload — asyncio.to_thread() means
     GET requests are served normally while an upload is in progress.

Q: There is no reason to replace the content of all tables every time we load
   an Excel file. We need to find a way to save all calculations in the tables.
   How will many people use the system? I want to aim for 500–1000 users.

A: You identified two real problems with the original design:

   1. Computed results (positions, violations, analytics) were thrown away on
      each upload. Activating a past upload required re-running the full
      pipeline from the stored file bytes — slow and wasteful.

   2. pg_try_advisory_lock(12345) is a GLOBAL lock. Only one upload at a time
      across the entire system. With 500 users, 499 of them get 409 during any
      active upload. This is a hard bottleneck.

   SOLUTION — two changes (ADRs 014, 015):

   Per-upload result storage (ADR 014):
   - Add upload_id FK to positions, violations, client_analytics.
   - Each upload's computed results are stored permanently under its upload_id.
   - Nothing is deleted on new upload — rows from old uploads remain.
   - Activate = instant flag flip (SET is_active = TRUE). No re-run. O(1).
   - All GET queries filter by the active upload_id for the current user.

   Per-user advisory lock:
   - pg_try_advisory_lock(user_id) instead of a fixed constant.
   - User 1 and User 2 can upload simultaneously — different locks, no conflict.
   - Same user cannot upload twice simultaneously — still serialised per user.

   User identity — UUID anonymous sessions (ADR 015):
   - Frontend generates UUID v4 on first load, stores in localStorage.
   - Every API request includes X-Session-Token: <uuid> header.
   - Backend creates a users row on first sight of a new token.
   - No passwords, no login page — stable identity per browser session.

   IMPORTANT CLARIFICATION — this is NOT aggregate mode:
   - Each upload is still processed independently.
   - FIFO runs only on that upload's transactions.
   - Switching between uploads shows results from that specific file only.
   - The data is NOT accumulated across uploads.

   DECISIONS: ADR 014 (per-upload storage), ADR 015 (UUID sessions).

SESSION 9 — REMOVING THE SECRETS ABSTRACTION (PR 1 cleanup)
────────────────────────────────────────────────────────────────────────────────

Q: If we do not plan to use secrets.py in this project, please delete the file
   and all mentions of it in the code.

A: Deleted `src/core/secrets.py` and reworked the foundation to read the DB
   password directly from `pydantic-settings`:

   - `Settings` gains a `db_password: SecretStr` field (required). pydantic
     populates it from `.env` locally and from OS env vars in CI / Docker.
   - `SecretStr` redacts the password in `repr(settings)` and in any
     accidental log output. The real value is reached via
     `.get_secret_value()`, used only by `_build_database_url()` in
     `src/core/database.py`.
   - `database.py` no longer imports anything secrets-related.
   - One ty suppression on `settings = Settings()` because pydantic-settings
     populates required fields from the environment, not the constructor —
     a known limitation that the type checker can't see through.

   This reverses the design recorded in Session 4 (Q14, "Strategy/Protocol —
   SecretsProvider protocol") and confirmed in Session 7 (ADR 005 was kept as
   a "defensible architecture decision"). Why reverse it now?

   - The abstraction had no second implementation. With only
     `EnvironmentSecretsProvider` shipping, the protocol added a layer of
     indirection that wasn't earning its keep.
   - `pydantic.SecretStr` already gives us the one safety property we cared
     about (no accidental logging) without a custom protocol.
   - Removing it shortens the foundation by one file and one moving part —
     useful given the assignment scope.

   The migration path to a real managed secrets backend (AWS / GCP / Vault)
   is documented in `docs/PRODUCTION_ROADMAP.md` §7. If that day comes,
   re-introducing a small Protocol around `Settings.db_password` is a
   one-file change.

SESSION 11 — IDENTITY MODEL PIVOT (mid-PR-2)
────────────────────────────────────────────────────────────────────────────────

Q: If it simplifies the codebase, I want every user to see all uploads.
   But a returning user should still see their last viewed file. The UUID
   approach has the problem that it doesn't follow the user across devices.

A: Both points correct. The tab-concern is fine (localStorage is shared
   across same-origin tabs); the cross-device gap is real.

Q: Should we add JWT? I know JWT better than SQL tables.

A: JWT will NOT simplify. It only changes how identity arrives at the
   server — every row of partitioning code stays the same. To make JWT real
   you also add: password storage, login/register endpoints, token expiry,
   refresh strategy, storage-vs-XSS tradeoffs. Strictly more code, not less.

Q: What if we detect the PC username via Active Directory / Kerberos?

A: Real pattern (Integrated Windows Authentication / SPNEGO) but requires
   server in AD domain + browser zone config + every reviewer to configure
   Kerberos on their evaluation laptop. Won't survive `docker compose up`
   on a non-domain-joined machine. The portable production version of this
   idea is OIDC SSO via the corporate IdP — but that's MORE complex, not
   less. The minimal portable miniature: type a corporate email once.

Q: What does email-as-identity take, and what are the tradeoffs?

A: Smaller than today. Decisions confirmed by user:
   1. pydantic.EmailStr for validation at the API boundary
   2. Drop the advisory lock entirely (concurrent uploads write distinct
      upload_ids; no shared rows mutated; no lock needed)
   3. Keep the header name X-Session-Token (scanner-friendly, JWT-shaped)
      — the value is now the corporate email rather than a UUID
   Emphasis on deployment context (corporate intranet) added to SPEC §0
   and AI_USAGE so any automated scanner reads the trust model in context.

A (implementation summary):
   - users: dropped session_token, added email UNIQUE +
     last_viewed_upload_id (FK ON DELETE SET NULL)
   - uploads: dropped user_id + is_active
