 ANSWER:

Great review — these are exactly the questions a tech lead would ask. Let me go through each
  one. I'll flag the ones that change the spec.

  ---
  1. Malicious Excel
  openpyxl with data_only=True never executes macros or formulas — it reads cell values only,
  so macro injection isn't a risk. We still need: (a) validate MIME type AND extension (not
  just filename), (b) enforce a max file size before parsing (e.g. 10MB), (c) run inside a
  try/except to handle corrupt/malformed files. I'll add a security section to the spec.

  2. Large row counts
  openpyxl has a read_only=True streaming mode that doesn't load the entire file into memory —
  we use that. For inserts, we do batch inserts (1000 rows per statement) rather than one
  INSERT per row. 7 columns × 10,000 rows is trivial. 7 columns × 1M rows is where streaming
  matters.

  3. Defective rows
  The assignment only says "validate" — it doesn't specify what to do with failures. Our call:
  reject the row (don't insert it), log it as an INVALID_VALUE violation, include it in the
  upload response summary. The data the user queried afterward will never include the bad row —
   only clean data enters the DB. Makes sense?

  4. Truncation order
  Explained below in #27 — see FK constraints. Short answer: it matters when there are FK
  constraints, and it's still good practice even when there aren't, so future constraints don't
   break anything.

  5 & 6. "Invalid" at insert vs FIFO
  You got it exactly right: "invalid for insertion" = failed row validation (bad qty, price,
  action). Sell-before-buy is detected by FIFO after the row is already in the DB. Two separate
   concepts, two separate stages. I'll make the data flow labels clearer in the spec.

  7. Volatility definition
  Your read ("client that holds a lot of different stocks") isn't what the assignment says. The
   exact words are "largest variation in total portfolio value" — meaning a client whose total
  portfolio dollar value swings the most over time. Our spec already implements this correctly
  (simulate value at each transaction timestamp, measure max − min). No change needed.

  8. Full violations report
  Yes — GET /api/v1/violations returns all violations. The client can filter by client_id or
  violation_type via query params. The frontend will show this in the ViolationsTable.

  9. Analytics scope
  All four required analytics are global (across all clients combined). Per-client data lives
  in GET /clients/{id}/positions. I'll add a couple of additional per-client analytics as bonus
   — see #21.

  10. Missing ADRs + ORM switch ← spec change
  Two things: (a) I'll add the PostgreSQL upgrade decision to the table. (b) Switching to
  SQLAlchemy ORM — this supersedes ADR 004. The assignment says ORM is preferred, and it'll

  want ORM?

  14. Design patterns
  Our architecture follows several named patterns deliberately:
  - Layered Architecture — api → domain → db, dependencies only point downward
  - Repository Pattern — db/repositories/ abstracts all data access behind functions
  - Dependency Injection — FastAPI deps.py injects DB connections into routes
  - Service Layer — domain/ contains pure business logic, no HTTP or DB knowledge
  - Strategy / Protocol — SecretsProvider protocol allows swapping backends

  15. database.py in core/ vs db/
  core/ is for cross-cutting infrastructure shared by the whole app (config, secrets, the
  engine). db/ is for domain-specific data access (schema, repositories). The SQLAlchemy engine
   and connection pool are infrastructure — they don't know anything about transactions or
  positions. I'll move it to db/ though, since that's where a new developer would look for it.
  Good catch.

  16. "domain" folder name
  It comes from Domain-Driven Design. The "domain" layer holds pure business logic — what the
  application does — with zero knowledge of HTTP or databases. fifo.py doesn't import
  SQLAlchemy. violations.py doesn't import FastAPI. This isolation is what makes unit testing
  trivial and the logic reusable. The name signals: "this is the core of the application, not
  plumbing."

  17. Testability

  DB, no HTTP client, no fixtures. db/repositories/ tests need a DB but no HTTP. api/routes/

  dependencies only flow downward and are injected, not imported directly.

  27. FK constraint errors
  A Foreign Key constraint is a database rule: "column A in table X must reference an existing
  row in table Y." Example: if violations.transaction_id were a real FK to transactions.id, you

  order is: delete the child tables first (violations, which reference transactions), then the
  parent (transactions). In our current schema, transaction_id in violations is TEXT with no FK
   declared — so there's no hard constraint — but we follow the correct order anyway so we can
  add proper FKs later without breaking anything.

  2. Scale, batch size, atomicity

  First, let's calculate what fits in a file. A 7-column xlsx is a ZIP of XML — at roughly 25
  bytes per row compressed, 50MB ≈ 2 million rows. That's genuine scale. Here's the full
  approach:

  - File size limit: 50MB — enforced before we touch the bytes
  - Row limit: 200,000 rows — checked during streaming (we stop and reject if exceeded)

  17. Injected vs imported dependencies

  Imported — the function reaches out and grabs what it needs:
  # tightly coupled — you can't test this without a real DB
  from src.db.database import get_engine

  def get_clients():
      with get_engine().connect() as conn:
          ...

  Injected — the dependency is handed in from outside:
  # loosely coupled — caller controls the dependency
  def get_clients(session: Session):
      ...

  # FastAPI does the injection automatically:
  @router.get("/clients")
  def get_clients(session: Session = Depends(get_session)):
      ...

  In tests, you override Depends(get_session) to inject a test database session. The route code
   never changes — the context changes. Without injection you can't swap the dependency; with
  it you can.

ANSWER:

1. I/O bound vs CPU bound — clear explanation

  Think of it this way:

  I/O bound — the code is waiting for something external. The CPU is idle.
  - SELECT * FROM transactions — Python sends the query, then sits doing nothing until
  PostgreSQL responds
  - Reading file bytes from the network — Python waits for the client's upload to arrive
  - → async/await helps here: while waiting for PostgreSQL, handle another incoming request

  CPU bound — the code is computing. The CPU is the bottleneck, never idle.
  - FIFO engine: sort 50,000 rows, iterate through a deque, do arithmetic on every row
  - openpyxl parsing: reads compressed XML, builds Python objects for every cell
  - → async/await does nothing here. The CPU is already maxed out. Waiting "asynchronously" for
   more CPU doesn't make sense.

  In our code specifically:

  ┌─────────────────────────────┬───────┬──────────────────────────────────┐
  │          Operation          │ Bound │               Why                │
  ├─────────────────────────────┼───────┼──────────────────────────────────┤
  │ GET /clients (DB query)     │ I/O   │ Waits for PostgreSQL             │
  ├─────────────────────────────┼───────┼──────────────────────────────────┤
  │ GET /analytics (DB queries) │ I/O   │ Waits for PostgreSQL             │
  ├─────────────────────────────┼───────┼──────────────────────────────────┤
  │ openpyxl parsing            │ CPU   │ Pure Python XML parsing          │
  ├─────────────────────────────┼───────┼──────────────────────────────────┤
  │ FIFO engine                 │ CPU   │ Sorting + iteration + arithmetic │
  ├─────────────────────────────┼───────┼──────────────────────────────────┤
  │ Bulk DB inserts             │ I/O   │ Waits for PostgreSQL to write    │
  └─────────────────────────────┴───────┴──────────────────────────────────┘

  Multiple cores for CPU-bound work? Technically yes — FIFO per (client_id, isin) pair is
  embarrassingly parallel (pairs are fully independent), so ProcessPoolExecutor could compute
  them simultaneously. But for realistic datasets (say 200 client+ISIN pairs at 1000 rows
  each), the overhead of spawning processes takes longer than the computation itself. Overkill
  for this assignment. Production path: move the heavy computation into PostgreSQL window
  functions, or use Dask for distributed processing.

  Decision for the spec: FastAPI automatically runs synchronous def routes in a thread pool —
  no async def needed for correctness. We use sync SQLAlchemy. Document the async upgrade path
  (asyncpg + SQLAlchemy async) in Production Scaling Notes.

  2. Queue for production — yes, adding that to the Production Scaling Notes section. The note

  Production fix is Celery + Redis: upload returns a job ID immediately, client polls for
