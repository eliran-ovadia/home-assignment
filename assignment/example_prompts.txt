AI ANSWER:

Really good question — and the answer depends on how deep you want to go. Let me lay out the complexity honestly.

  ---
  The core problem: FIFO doesn't work per-file

  FIFO cost basis is stateful across time. If Client A buys 100 shares of ISIN X in upload 1, then sells 50 in upload
  2 — the sell can only be calculated correctly if we have both uploads' data together. There's no meaningful
  "single-file FIFO result" in isolation.

  So positions and violations must always be computed on all data. Per-file analytics would be a different, lighter
  thing.

  ---
  What "aggregate + per-file" actually looks like

  Add one new concept: an uploads table. Each upload gets a record, and every transaction references its upload.

  ┌───────────────────────────────────────────────────────────────┬───────────────────────────────┐
  │                             What                              │          How complex          │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ uploads table + upload_id on transactions                     │ Low — one extra table, one FK │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Positions/violations computed on ALL data (always)            │ Same as replace — no change   │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ GET /uploads — list past uploads with stats                   │ Low                           │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ GET /uploads/{id}/transactions — what was in that file        │ Low                           │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Per-upload analytics (FIFO isolated to one file)              │ Very hard / misleading — skip │
  ├───────────────────────────────────────────────────────────────┼───────────────────────────────┤
  │ Per-upload violations (which violations were NEW this upload) │ Medium — doable but complex   │
  └───────────────────────────────────────────────────────────────┴───────────────────────────────┘

  ---
  My honest recommendation

  Go with aggregate mode (append, deduplicate by TransactionId) and add upload tracking — but keep analytics global
  only. This gives you:

  - A system that feels alive and production-like
  - Upload history in the UI ("you've uploaded 3 files, here's each one")
  - Correct FIFO computed across all history
  - Analytics on everything seen so far

  What you don't get (and don't need to promise): per-upload P&L or per-upload analytics. That's a scope that could
  consume days.

  ---
  But — I want to flag the risk: this adds ~25% complexity to the backend and means the spec gets more involved. Given
   the 3-5 hour estimate, the simpler replace-on-upload approach would let you focus that time on getting FIFO,
  violations, and the frontend right, which is where you'll be evaluated.

  My vote: if you're confident in the timeline, go aggregate. If you're worried about time, go replace — and note in
  AI_USAGE.md that you considered aggregation and made a deliberate call.
